Automation & Modern Tech Vision

The site works — but everything runs through one person. These four changes give time back to the people who've been doing things the hard way, and show what each one actually looks like to use.

The Problem: Everything Is Manual

The site works, but almost nothing happens on its own. Every task flows through the webmaster or Paul:

🔁 Renewal Reminders

351 members are more than two years lapsed and have never once received a reminder. Someone has to notice, look them up, and write to them individually — or it just doesn't happen.

📝 Officer Profiles

An officer moves institutions. She emails the webmaster. He logs in, finds the record, updates it, replies to confirm. Fifteen minutes of back-and-forth for a two-field change.

📰 Newsletter Publishing

The editor emails a PDF with metadata in the body of the message. The webmaster logs in, transcribes everything by hand, and hopes he didn't mistype the issue number.

📊 Financial Visibility

Before every board meeting, the treasurer emails to ask how many members have paid. Someone runs a query. The number goes into an email. Repeat next quarter.

📧 Automated Renewal Reminders

❌ Currently
  1. Officer reviews dues tracker by hand
  2. Figures out who's overdue from memory or spreadsheet
  3. Writes individual reminder emails
  4. Sends them — or runs out of time and doesn't
Time: ~2 hours/month  |  Result: 20–30% delinquency
✅ With automation
  1. A scheduled job runs every night
  2. Checks who expires in 60 / 30 / 0 days
  3. Sends a tailored email to each group automatically
  4. Logs every message sent so there's an audit trail
Time: Zero ongoing  |  Result: far fewer lapses

How it works

  • Scheduled job runs nightly — queries the existing MySQL members table, no new data to maintain
  • Three triggers: 60-day warning, 30-day warning, and an expiry-day notice
  • Delivery via SendGrid with proper SPF/DKIM records so messages land in inboxes, not spam folders
  • Audit log: every email is stored in an email_log table — who got what and when
  • Opt-out link in every email, one click, no login required

👤 Officer Self-Service Profiles

❌ Currently
  1. Officer emails: "I moved — new phone is…"
  2. Webmaster logs into the admin panel
  3. Finds the record, edits the fields
  4. Replies to confirm it's done
  5. Officer waits a day or two for each small change
Time: 10–15 min per change  |  Friction: officer waits on you
✅ With self-service
  1. Officer clicks "Edit My Profile" on her member page
  2. Form opens pre-filled with her current info
  3. She changes what's out of date and hits Save
  4. The public officer listing updates immediately
  5. No email, no waiting, no middleman
Time: 2 min, start to finish  |  Friction: none

How it works

  • The form pre-fills from the existing member record — the officer sees her current data, not a blank slate
  • Validation happens as she types — a malformed email address gets flagged before she even tries to save
  • On Save, a PATCH request updates the database directly — no page reload, change is visible in under a second
  • The public officer listing reads from the same table, so it's always current without any extra steps
  • Optional: changes can sit in a pending queue for webmaster review before going live — useful during the transition

📰 Newsletter Self-Publishing

❌ Currently
  1. Editor emails a PDF with metadata written out in the message body
  2. Webmaster logs into admin and opens the newsletter upload form
  3. Types in Season, Year, Issue #, Author, Title by hand
  4. Uploads the file, clicks Save
  5. Hopes he typed Issue 44 and not Issue 43
Time: 10–15 min  |  Error rate: higher than it should be
✅ With direct publishing
  1. Editor opens "Publish Newsletter" from her member page
  2. Season and Year are pre-filled; issue number is calculated automatically
  3. She drags the PDF into the drop zone
  4. Fills in title and author, clicks Publish
  5. Archive updates; members get a notification email
Time: 3 min  |  Error rate: zero for the issue number

How it works

  • File validation runs before anything uploads: wrong file type or oversized PDF gets flagged immediately
  • Member notification is opt-in per issue — if checked, it queues a batch email to all active members
  • Role-gated: the page is only visible to users with the newsletter_editor role

How it works

  • Everything comes from the existing MySQL database — no new schema, no data migration
  • Sorting and filtering are instant — the full dataset loads once; React handles the rest client-side without hitting the server again
  • The revenue bars are CSS-only — no charting library needed for this level of display
  • "Send Reminder" queues an email to that member immediately; "Send Bulk Reminder" does the whole overdue list at once
  • "Export CSV" is a direct browser download — treasurer opens it in Excel or imports it to whatever the board uses

⚛️ Why React?

⚡ No Page Reloads

Click Save — the data saves in the background. No white flash, no waiting. A confirmation appears in place.

Better UX

✅ Inline Validation

The email field turns red the moment the format is wrong — before you even try to submit. No "please try again" after a page reload.

Fewer Errors

📱 Works on Phones

An officer updating her profile from her phone at Kalamazoo gets the same experience as at a desktop. Forms reflow, touch targets are large.

Mobile-Ready

🔄 Live Data

The treasurer dashboard refreshes on its own. She doesn't need to reload the page to see who paid this morning.

Always Current

🔗 Easy to Extend

Once the site talks through APIs, adding ORCID, Zotero, or Stripe later is a new endpoint — not a rewrite of pages that already work.

Future-Proof

🧩 Shared Components

The member form, officer form, and newsletter form all use the same building blocks. Write it once, change it in one place.

Less Maintenance

🏗️ How We Get There

The whole site doesn't need to change at once. The old PHP keeps running while each new piece goes live beside it. If something goes wrong, you roll back that one component — nothing else is affected.

Phase 1 · Now

Stabilize

Fix the known glitches, set up backups, update stale content. No new features yet — just get the foundation solid before building on it.

Phase 2a

API Layer + Reminders

Lay a thin API over the existing MySQL database. Add the renewal reminder job. Fix email delivery properly while we're in there.

Phase 2b

Self-Service Forms

Officer profile editing. Newsletter publishing. Role-based access so editors and officers can do their own work without going through the webmaster.

Phase 2c

Treasurer Dashboard

Real-time membership view, bulk reminders, CSV export. The treasurer stops emailing questions she should be able to answer herself.

Phase 3

Scholarly Features

Living bibliography, dissertation registry, ORCID integration, rich member profiles. This is where the site becomes something the field actually uses.

The key point: this isn't a redesign. It's replacing the manual bottlenecks one at a time — keeping Paul's database and the PHP pages that work, and adding the pieces that let officers and editors do their own work. The site stays live the whole time.
